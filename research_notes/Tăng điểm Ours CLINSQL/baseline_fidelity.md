## Q1. CLINSQL CoT + self-refinement baseline: how it works and what settings it uses

### Takeaway
The original CoT baseline makes one generation call with the full MIMIC-IV schema text. If BigQuery fails to execute the query, it runs up to 2 refinement rounds, and each round gets the **raw BigQuery exception string** (`str(e)`). Refinement happens only on execution failure, never on empty or wrong results. For GPT-5-mini the code uses Azure Chat Completions with `temperature=1.0`. It sets **no max-token limit and no reasoning_effort**, so the API defaults apply.

### Cited Findings
**Prompt structure**
- The generation prompt is one user message (no system message): "You are a clinical data analyst expert specializing in the MIMIC-IV database. Your goal is to produce a correct BigQuery SQL query…". It then gives Constraints (target BigQuery; datasets `physionet-data.mimiciv_3_1_hosp` and `physionet-data.mimiciv_3_1_icu`), "MIMIC-IV Schema Reference (HOSP + ICU)" (the whole `mimic4_schema.txt`), and the clinical question in quotes. The output format is "Reasoning:" (think step by step about tables, joins, filters, groupings, edge cases) followed by an SQL fenced block. — [prompt_utils.py](https://github.com/Barryshen1/ClinSQL/blob/main/utils/prompt_utils.py)
- The refinement prompt says: "The following SQL failed to run on Google BigQuery. Refine it to resolve the error and better answer the question." The constraints are valid BigQuery, the correct datasets, and "Modify only what is necessary; prefer minimal, correct fixes." It then gives the schema, the question, "Previous SQL attempt" in an sql fence, and "BigQuery error message:\n{error_message}". The output is Reasoning (explain cause of error and fix) plus a fenced SQL block. — [prompt_utils.py](https://github.com/Barryshen1/ClinSQL/blob/main/utils/prompt_utils.py)
- Schema text is loaded once and included in **both** the generation and the refinement prompts. — [clinical_sql_benchmark_evaluator_CoT.py](https://github.com/Barryshen1/ClinSQL/blob/main/model_inference/clinical_sql_benchmark_evaluator_CoT.py)
- SQL extraction takes the **last** fenced code block. If there is none, it falls back to `[sql]` tags, then to the trailing `WITH…`/`SELECT…` text. It strips everything before the first WITH/SELECT and appends `;`. — [sql_utils.py](https://github.com/Barryshen1/ClinSQL/blob/main/utils/sql_utils.py)
- The paper describes the same thing: two regimes (Direct Output, and CoT with a "Reasoning:" section plus a fenced SQL block), and "up to two refinement rounds", each getting the question, the prior SQL and the BigQuery error message, with minimal-edit instructions. — [arXiv 2601.09876](https://arxiv.org/html/2601.09876)

**Self-refinement loop**
- `max_refinement_attempts: int = 2`. The loop condition is `while not success and attempt_num < 1 + self.max_refinement_attempts`, so there are at most 3 executions (1 initial plus 2 refinements). — [CoT evaluator](https://github.com/Barryshen1/ClinSQL/blob/main/model_inference/clinical_sql_benchmark_evaluator_CoT.py)
- Refinement triggers **only on execution failure** (`success == False`, meaning BigQuery raised an exception). Successful queries, including those that return empty results, are not refined. — same file
- The error fed back is `refine_err = error or "Execution failed"`, where `error = str(e)` from the BigQuery client exception. That is the **raw, unfiltered BigQuery error text**. — same file (`SQLExecutor._execute_sql`)
- Each refinement round refines the **latest** failing SQL, not the original. If the refinement call returns an empty string (an API error or an empty response), the loop `break`s early. — same file
- BigQuery execution settings: `use_query_cache=True`, `maximum_bytes_billed = 50 GB`, `query_job.result(timeout=300)` seconds. There is no LIMIT injection and no SQL guard or whitelist. — same file
- Initial generation failure: if `generate_sql` returns "", the sample is recorded with `"error": "Failed to generate SQL"`, and no refinement happens. — same file

**Model and API settings for GPT-5 family**
- The `GPT-5-mini` spec is `provider="azure_openai"`, `api_model/azure_deployment="GPT-5-mini"`, `default_temperature=1.0`, `use_responses_api=False` (so Chat Completions), and `azure_api_version="2024-12-01-preview"`. `GPT-5` is actually mapped to the **`gpt-5-chat`** deployment, the non-reasoning chat model. — [model_specs.py](https://github.com/Barryshen1/ClinSQL/blob/main/utils/model_specs.py)
- The Chat Completions call is `client.chat.completions.create(model=..., messages=[{"role":"user","content":prompt}], temperature=temp)`. It passes **no `max_tokens`, no `max_completion_tokens` and no `reasoning_effort`**. If the API says temperature is "unsupported", it retries with 1.0. — [CoT evaluator](https://github.com/Barryshen1/ClinSQL/blob/main/model_inference/clinical_sql_benchmark_evaluator_CoT.py)
- Only o4-mini and GPT-4.1 use the Responses API, with `max_output_tokens=2048`. Mistral uses `temperature=0.1, max_tokens=2048`. — same file / model_specs.py
- The paper lists the GPT-5-mini version as `gpt-5-mini-2025-08-07` through the official API. Proprietary models were run via official APIs and open models via vLLM. — [arXiv 2601.09876](https://arxiv.org/html/2601.09876)
- Inference is sequential. Model names are passed to the evaluator through `run_proprietary_models.sh`, and Azure env vars are required. — [run_proprietary_models.sh](https://github.com/Barryshen1/ClinSQL/blob/main/model_inference_scripts/run_proprietary_models.sh)

**How failures are saved and scored**
- In the saved output, the final SQL is the last attempted SQL, **even if it failed** (`"sql": sql if success or sql else ""`). If generation produced nothing, the SQL file contains `-- SQL Generation Failed: <error>`. If there is no successful non-empty dataframe, the result CSV is a placeholder `pd.DataFrame({"result":[None]})`. — [CoT evaluator](https://github.com/Barryshen1/ClinSQL/blob/main/model_inference/clinical_sql_benchmark_evaluator_CoT.py)
- The scorer still runs the **SQL rubric on a failed SQL**, so a non-executing query can earn partial SQL-rubric credit. It also runs the results rubric on the `{"result": None}` CSV. Scores are the mean over **all** samples (failures count as their judged score, usually 0 for results). — [clinical_rubric_scorer.py](https://github.com/Barryshen1/ClinSQL/blob/main/evaluation/clinical_rubric_scorer.py)
- Rubric aggregation: if any critical child scores below 1.0, the node scores 0. Otherwise non-critical children are weight-averaged. "Sequential" nodes accumulate in order and stop at the first child below 1.0. Leaf scores are binary (0 or 1) from the LLM judge. — same file
- The judge is the Azure deployment `gpt-5-chat` (the only supported value), called with `temperature=0.2` and a 1024-token cap. It tries `max_completion_tokens` and then `max_tokens`, and waits 0.8 s between calls. The paper calls the judge "GPT-5". — [scorer](https://github.com/Barryshen1/ClinSQL/blob/main/evaluation/clinical_rubric_scorer.py); [paper](https://arxiv.org/html/2601.09876)
- Reported GPT-5-mini scores (Table 4): test average SQL 42.72 / Execution 74.67; validation average SQL 42.30 / Execution 75.16. Test by difficulty, Execution: Easy 81.31, Medium 73.46, Hard 69.69. — [arXiv 2601.09876](https://arxiv.org/html/2601.09876)

### Inferences
- **Deviation in the local reproduction (error feedback):** the original feeds the raw `str(exception)` from BigQuery, which typically includes the message, location such as `[line:col]`, and the job ID. The local version feeds only whitelisted error classes, which gives the model less information than the original. This is a reproduction deviation, not part of the method, and it plausibly *lowers* CoT's refinement success. It should be disclosed, or the comparison should give CoT at least a sanitized message text (for example, the BigQuery error message with job IDs and project IDs removed). BigQuery error messages describe the schema or syntax, not patient data, so a sanitized raw message may still meet the data-protection constraint. This is my judgement, not a sourced claim.
- **Token and reasoning settings:** the original lets gpt-5-mini run with the API defaults: no output cap and the default reasoning effort. If the local run sets `max_completion_tokens` low, it can produce empty responses (see Q3). In the original, an empty response counts as "Failed to generate SQL" with no retry. A local cap is therefore a deviation, unless it is large enough never to bind.
- `temperature=1.0` is the only value GPT-5 reasoning models accept. Passing it or omitting it is equivalent.
- The refinement trigger in the local run should be execution failure only. Refining on empty results would change the method.
- The scoring pipeline gives SQL-rubric credit even to failed SQL. A local scorer that sets the SQL score of failures to 0 deviates from it, in a direction that is pessimistic for all methods.

### Gaps
- The paper text I read did not state decoding settings or an explicit failure-scoring rule. The code is the only evidence, and the GitHub `main` branch could differ from what produced the paper numbers.
- I could not verify that the `GPT-5-mini` Azure deployment used `gpt-5-mini-2025-08-07` with the default `reasoning_effort` (medium). The code passes none, so the default applies, but the exact default for that Azure deployment is not stated in the sources I read.
- `copy_rubric_trees` copies only the rubric JSONs into the output folder, so `gold_sql.sql` and `gold_results.csv` are probably absent at scoring time, and the judge sees only rubric requirements, the model SQL and the model rows. I did not verify whether gold files are placed there by another step.
- The repo has 0 issues and 1 PR ("docs: improve README"), so no bug reports exist. — [GitHub API](https://github.com/Barryshen1/ClinSQL/pulls)

## Q2. SDE-SQL: pipeline stages and exact settings

### Takeaway
The official code (Bird template) uses `engine=qwen-max` by default, base `temperature=0.3`, `try_num=3`, self-consistency with **n=9** candidates in one API call at `max_tokens=4096`, two-phase probe exploration before generation, and refinement up to 3 rounds. Refinement fixes SQL execution errors with the **raw SQLite error text** and fixes empty results with Sub-SQL/probe diagnosis. Probes report only `NULL`, `Not NULL` or "There are some SQLite errors." They never abort; invalid probes are passed to the LLM as information. The paper itself gives no numbers for n, temperature, refinement limits or cost.

### Cited Findings
**Paper-level description**
- There are three parts: (1) Schema Linking (few-shot entity extraction, an LSH plus semantic value retriever, a one-shot column selector; unselected columns keep only name and type); (2) SQL Generation with two-phase self-driven exploration (Candidates exploration with Base and Condition SQL probes, then Combinations exploration) followed by zero-shot generation and self-consistency; (3) Refinement, applied to empty results: error-cause identification via an SQLGlot AST decomposer into Sub-SQLs, solution exploration with probes over five error causes, modification, then target checking that removes unnecessary SELECT columns. — [arXiv 2506.07245v2](https://arxiv.org/html/2506.07245v2)
- The main model is Qwen2.5-72B-Instruct. BIRD dev EX is 67.67 zero-shot and 68.19 with SFT, against a vanilla baseline of 60.17. Removing exploration in both generation and refinement gives 64.47. — [arXiv 2506.07245v2](https://arxiv.org/html/2506.07245v2)
- The paper states **no** self-consistency sample count, temperature, refinement limit, or cost/latency figures. It only says "selects the most consistent answer". — [arXiv 2506.07245v2](https://arxiv.org/html/2506.07245v2)

**Settings in the official run script and code**
- `run/run_qwen_eval_template.sh` uses `ENGINE=qwen-max`, `TEMPERATURE=0.3`, `TRY_NUM=3`, `use_knowledge=False`, `no_cot=True` (passed as `--chain_of_thought`), `use_judge=False`, `judge_target=True`, `use_desc=True`, `use_refine=True`, `use_check=False`, `use_probe=True`, `use_selected_examples=False`, `use_selfconsistency=True`. — [run_qwen_eval_template.sh](https://github.com/Lancelot-Xie/SDE-SQL/blob/main/run/run_qwen_eval_template.sh)
- Generation with self-consistency is `connect_gpt(engine, prompt, max_tokens=4096, temperature=temperature + cur_try_num*0.1, n=9)`, which is **9 candidates in a single API call using the `n` parameter**. The temperature is 0.3 on the first pass. Without self-consistency, it makes one call at the same temperature. — [gpt_request.py](https://github.com/Lancelot-Xie/SDE-SQL/blob/main/src/gpt_request.py)
- `connect_gpt` sends a system message "You are a helpful SQL assistant." plus the user prompt, and calls `client.chat.completions.create(model, messages, max_tokens, temperature, n)`. Any exception is turned into the string `'error: <e>'` and passed through `extract_sql`. — [gpt_request.py](https://github.com/Lancelot-Xie/SDE-SQL/blob/main/src/gpt_request.py)
- **Self-consistency vote** (`find_most_consistent_sql`): each candidate is executed with a 30 s timeout. Failures and timeouts give the result `[]`. Results are keyed by `frozenset(rows)`, which is order-insensitive and removes duplicates. The winner is the largest group with a **non-empty** result, and its first SQL is returned. If every candidate failed or returned empty, the fallback is `sql_list[0]`. — [uils.py](https://github.com/Lancelot-Xie/SDE-SQL/blob/main/src/uils.py)
- **Exploration** (`probe_before_generation`): stage 1 prompt produces a JSON of candidate probes (temperature 0.3, max_tokens 4096) and executes them. Stage 2 prompt receives the stage-1 probe results and produces combined probes, which are executed. Both result blocks go into the generation prompt. — [explore_new.py](https://github.com/Lancelot-Xie/SDE-SQL/blob/main/src/explore_new.py)
- **Probe result format:** each probe is reported as `"<sql>: 【NULL】"`, `"【Not NULL】"` or `"【There are some SQLite errors.】"`. No rows and no raw error text are shown in generation-time probes. The probe SQL is also rewritten (`|| ' ' ||` becomes `,`, and `ASC LIMIT` becomes `ASC NULLS LAST LIMIT`). An invalid probe **does not abort**; the error is reported as information. — [explore_new.py](https://github.com/Lancelot-Xie/SDE-SQL/blob/main/src/explore_new.py)
- Refinement-time probes (`probe_sqls` in refine_new.py) use the same NULL / Not NULL / "There are some SQLite errors." encoding. The generation-time `probe_sqls` variant in explore_new.py passes the raw `sqlite_error`, but the two-stage functions actually used pass the generic message. — [refine_new.py](https://github.com/Lancelot-Xie/SDE-SQL/blob/main/src/refine_new.py); [explore_new.py](https://github.com/Lancelot-Xie/SDE-SQL/blob/main/src/explore_new.py)
- Probe and final SQL execution (`uils.execute_sql`) uses a **3 s timeout** and returns only `data: result[:5]` (first 5 rows) plus columns. On error it returns `sqlite_error = ' '.join(er.args)`, the raw SQLite message. — [uils.py](https://github.com/Lancelot-Xie/SDE-SQL/blob/main/src/uils.py)
- **Refinement** (`refine_sql`, with `max_try_times = try_num = 3`) is triggered by `is_need_refine` when:
  - execution raises an error or times out (`data is None`), in which case `fix_error` is called with **the raw `sqlite_error` text** in `error_result_prompt` ("When executing SQL below, some errors occurred…" plus the schema, PK/FK, question, evidence, old SQL and error);
  - the result is empty, which sets `sqlite_error='no data selected'` and calls `probe_refine_sql`. That step splits the SQL into Sub-SQLs with an AST decomposer (60 s timeout; on failure an LLM `search_prompt` generates them), runs diagnose probes, has the LLM propose fix probes, runs them, and then the `empty_result_prompt` with both probe blocks produces the fixed SQL;
  - the result has more than one row and some, but not all, values are NULL (message: "exist None value, you can add `IS NOT NULL`…").

  A single-row result never triggers refinement. The loop ends at 3 refinement attempts. — [refine_new.py](https://github.com/Lancelot-Xie/SDE-SQL/blob/main/src/refine_new.py)
- **Target checking** (`judge_target`, enabled by `judge_target=True`) runs only when the first SQL needs no refinement. It shows the result column names to the LLM. With self-consistency on, it samples **n=3** at temperature 0.3 and applies the modification only if at least 2 of 3 votes say "Modification": "True". — [refine_new.py](https://github.com/Lancelot-Xie/SDE-SQL/blob/main/src/refine_new.py)
- All refinement LLM calls use `max_tokens=4096, temperature=0.3`. — [refine_new.py](https://github.com/Lancelot-Xie/SDE-SQL/blob/main/src/refine_new.py)
- With `use_check=False`, the outer `while cur_try_num < try_num` loop runs once (`check_pass=True` causes a break). So `try_num=3` effectively only caps refinement rounds. — [gpt_request.py](https://github.com/Lancelot-Xie/SDE-SQL/blob/main/src/gpt_request.py)
- Concurrency is `max_workers = 1`. Per-question time is logged as probe, generation and refinement time to `time_details.jsonl`, but no aggregate cost or latency is published. — [gpt_request.py](https://github.com/Lancelot-Xie/SDE-SQL/blob/main/src/gpt_request.py)
- Evaluation is standard BIRD EX: `set(pred) == set(gold)` with a 30 s timeout per query (`META_TIME_OUT=30.0`). Errors and timeouts score 0. — [evaluation.py](https://github.com/Lancelot-Xie/SDE-SQL/blob/main/src/evaluation.py); [run_eval.sh](https://github.com/Lancelot-Xie/SDE-SQL/blob/main/run/run_eval.sh)

**Number of LLM calls per question (counted from the code; not reported in the paper)**
- Without refinement: 2 exploration calls (more if JSON parsing fails), 1 generation call with n=9, and 1 target-check call with n=3. Each refinement round adds 1 call for an execution-error fix, or 2 to 3 calls for an empty-result probe fix (an optional search_prompt, a fix-probe prompt and the final prompt). Up to 3 rounds. — derived from [gpt_request.py](https://github.com/Lancelot-Xie/SDE-SQL/blob/main/src/gpt_request.py), [refine_new.py](https://github.com/Lancelot-Xie/SDE-SQL/blob/main/src/refine_new.py)

### Inferences
- **SQL-guard rejections:** the original never aborts on a failing SQL or probe. Execution failures of the final SQL go back to the LLM as raw error text, and failing probes are reported as "There are some SQLite errors." The local change from aborting to feedback therefore matches the original. Feeding whitelisted error classes instead of raw text is milder than the original for the final-SQL `fix_error` path, but equivalent to the original for probes, which only ever saw a generic error string.
- **Information level of probes:** original probes reveal only emptiness or non-emptiness, not row values. A local version that shows probe rows to the LLM is a stronger variant than the original.
- **Timeouts and row caps:** the original uses a 3 s execution timeout and 5 rows on SQLite (BIRD). On BigQuery a 3 s timeout would be impractical, so a longer timeout is a necessary adaptation and should be documented. The 5-row truncation only affects the NULL check and the target-checker inputs.
- **Self-consistency on BigQuery:** 9 candidates plus up to 3 refinements, each probe executed, can mean dozens of BigQuery jobs per question. The vote needs full result sets (frozenset of all rows). A local version that votes on truncated results deviates from the original.
- **Empty-result vs error priority:** a local version that also refines single-row results, or skips the NULL-value trigger, deviates from the original.

### Gaps
- The paper reports no cost, latency or token numbers. The repo logs time per question but publishes no aggregate figures.
- The repo default engine is `qwen-max`, while the paper reports Qwen2.5-72B-Instruct (the vLLM or SiliconFlow path). I found no record of the exact run configuration used for the paper numbers.
- The schema-linking stage (LSH value retrieval, column selection) depends on precomputed `data/match_content.json` and `database_schema_dev.json`. I did not trace how those are produced. The repo's `data/README.md` was not read.

## Q3. Adaptations needed for GPT-5 family reasoning models (gpt-5-mini)

### Takeaway
On GPT-5 reasoning models, `temperature` (other than the default 1), `top_p`, penalties, logprobs, logit_bias and `max_tokens` are unsupported. Chat Completions requires `max_completion_tokens`, and this cap covers reasoning tokens plus visible output. A low cap can produce an empty or incomplete answer. `reasoning_effort` is supported, and its default depends on the model. Both baselines' original code passes `max_tokens` and/or `temperature` (SDE: `max_tokens=4096, temperature=0.3`, `n=9`), so a faithful gpt-5-mini run must remap these parameters.

### Cited Findings
- Azure OpenAI docs: "Reasoning models other than GPT-6 Astra don't support the following parameters: `temperature`, `top_p`, `presence_penalty`, `frequency_penalty`, `logprobs`, `top_logprobs`, `logit_bias`, `max_tokens`." — [Microsoft Learn, Azure OpenAI reasoning models](https://learn.microsoft.com/en-us/azure/ai-foundry/openai/how-to/reasoning)
- "Reasoning models will only work with the `max_completion_tokens` parameter when using the Chat Completions API. Use `max_output_tokens` with the Responses API." Both caps cover reasoning, visible output and formatting tokens. — [Microsoft Learn](https://learn.microsoft.com/en-us/azure/ai-foundry/openai/how-to/reasoning)
- `reasoning_effort` values vary by model (`none`, `minimal`, `low`, `medium`, `high`, `xhigh`, `max`), and "`minimal` works only with the original GPT-5 reasoning models". Defaults vary by model. — [Microsoft Learn](https://learn.microsoft.com/en-us/azure/ai-foundry/openai/how-to/reasoning)
- OpenAI reasoning guide: "OpenAI recommends reserving at least 25,000 tokens for reasoning and outputs when you start experimenting with these models". If the cap is hit, the response has `status: incomplete` with reason `max_output_tokens`, which "might occur before any visible output tokens are produced". Code should check for empty `output_text`. — [OpenAI reasoning guide](https://developers.openai.com/api/docs/guides/reasoning)
- Community and third-party reports: gpt-5 rejects `max_tokens`; empty responses appear when all tokens go to reasoning; reports conflict on whether `temperature=1` is accepted (default-only) or any temperature is rejected for gpt-5/-mini/-nano. — [Braintrust KB](https://braintrust.dev/docs/kb/temperature-parameter-included-in-gpt-5); [OpenAI community: Temperature in GPT-5 models](https://community.openai.com/t/temperature-in-gpt-5-models/1337133); [graphiti issue #874](https://github.com/getzep/graphiti/issues/874)
- A third-party guide lists `n > 1` and `seed` as unsupported on GPT-5 models. I did **not** verify this against OpenAI's official API reference. — [apisrouter GPT-5 parameters guide](https://apisrouter.com/gpt-5-api-parameters-guide-unsupported-parameter-fixes)
- CLINSQL's own code handles this by passing `temperature=1.0`, retrying at 1.0 on an "unsupported" error, and passing no token cap. The CLINSQL judge tries `max_completion_tokens` first, then `max_tokens`. — [CoT evaluator](https://github.com/Barryshen1/ClinSQL/blob/main/model_inference/clinical_sql_benchmark_evaluator_CoT.py); [scorer](https://github.com/Barryshen1/ClinSQL/blob/main/evaluation/clinical_rubric_scorer.py)

### Inferences
- **For CoT, to match the original:** use temperature 1 or omit it, the default reasoning_effort (do not set it, or set `medium`, assuming medium is the default for gpt-5-mini; verify), and no cap or a very large `max_completion_tokens` (25k or more). If you set a lower cap, treat it as a deviation. Count how many samples end with empty output or `finish_reason=length`.
- **For SDE, faithful remapping:** `max_tokens=4096` becomes `max_completion_tokens`. 4096 is too small for a reasoning model, because reasoning tokens count toward it, so a larger cap is justified as an API adaptation, not a method change. `temperature=0.3 + 0.1*try` has to be dropped (temperature fixed at 1). That makes the 9 candidates *more* diverse than in the original, which is an unavoidable adaptation and should be documented. If `n=9` is not accepted, issue 9 independent calls. This is equivalent in distribution, but costs 9 times the input tokens.
- Use the same `reasoning_effort` across all methods (CoT, SDE, Ours). Otherwise differences in model compute confound the method comparison.

### Gaps
- I did not find an authoritative statement in OpenAI's own docs on whether gpt-5-mini accepts `n>1` on Chat Completions, or on its exact default `reasoning_effort`. Confirm both with a live test call: send `n=2` and check `len(choices)` and `usage.completion_tokens_details.reasoning_tokens`.

## Q4. Reported issues and bugs in the public repos

### Takeaway
Neither repo has filed issues. Reading the code reveals several latent bugs, mostly in SDE-SQL: missing API retry, an infinite retry loop, hard-coded skipped indices, and a broken path when the n=9 call fails. CLINSQL has a judge-parsing fallback that can score errors as 1. These matter when deciding which behaviours to copy faithfully and which to fix while documenting the change.

### Cited Findings
- CLINSQL: 0 issues, 1 PR (#1, "docs: improve README"). — [ClinSQL PRs](https://github.com/Barryshen1/ClinSQL/pull/1)
- SDE-SQL: `open_issues: 0`; repo created 2026-04-18, last push 2026-04-21. — [GitHub API repo metadata](https://api.github.com/repos/Lancelot-Xie/SDE-SQL)
- **SDE bug, no API retry:** in `gpt_request.py` the `@backoff.on_exception(...)` decorator sits above commented-out code and therefore decorates `extract_json`, not `connect_gpt`. API errors are caught inside `connect_gpt` and returned as the string `'error: …'`, which then becomes the "SQL". — [gpt_request.py](https://github.com/Lancelot-Xie/SDE-SQL/blob/main/src/gpt_request.py)
- **SDE bug, n=9 failure path:** when the n=9 call raises, `connect_gpt` returns a single string rather than a list. `find_most_consistent_sql` then iterates over the characters of that string. — [gpt_request.py](https://github.com/Lancelot-Xie/SDE-SQL/blob/main/src/gpt_request.py); [uils.py](https://github.com/Lancelot-Xie/SDE-SQL/blob/main/src/uils.py)
- **SDE bug, possible infinite loop:** `while sql_dict_1 == {} and try_times <= 5:` re-queries the LLM but never increments `try_times`, so a model that keeps returning unparsable JSON loops forever. The same applies to `sql_dict_2`. — [explore_new.py](https://github.com/Lancelot-Xie/SDE-SQL/blob/main/src/explore_new.py)
- **SDE leftover, hard-coded skip:** `finished_ids = list(finished_ids) + [i for i in range(0, 1000)]` marks indices 0 to 999 as done, so a fresh run only processes questions from index 1000 onward. There are many commented-out variants of this line, which suggests the authors ran BIRD dev in shards. — [gpt_request.py](https://github.com/Lancelot-Xie/SDE-SQL/blob/main/src/gpt_request.py)
- **SDE, use of gold during inference (logging only):** the non-self-consistency path calls `execute_model(sql, gt_list[i], …)` against the gold SQL, only to decide whether to write the prompt and output to `input_output.jsonl` (SFT data collection). It does not affect predictions. — [gpt_request.py](https://github.com/Lancelot-Xie/SDE-SQL/blob/main/src/gpt_request.py)
- **SDE, inconsistent clients:** `api_client.py` reads keys from environment variables, but `connect_gpt` in `gpt_request.py` hard-codes `api_key=""` for the deepseek (geekai.co) and qwen (dashscope) paths and only uses `OPENAI_API_KEY` for OpenAI models. — [api_client.py](https://github.com/Lancelot-Xie/SDE-SQL/blob/main/src/api_client.py); [gpt_request.py](https://github.com/Lancelot-Xie/SDE-SQL/blob/main/src/gpt_request.py)
- **CLINSQL judge-parse fallback:** if the judge reply can't be parsed, `score = 1.0 if "1" in response else 0.0`. After both API attempts fail, the response is the string `"Error: <exc>"`, so an API error message containing the digit "1" (for example, a 401 or 429 with a request ID) would be scored **1**. — [clinical_rubric_scorer.py](https://github.com/Barryshen1/ClinSQL/blob/main/evaluation/clinical_rubric_scorer.py)
- **CLINSQL early-break on empty refinement:** an empty model reply during refinement ends the loop and keeps the previous failed SQL, so there is no retry on API errors in inference. — [CoT evaluator](https://github.com/Barryshen1/ClinSQL/blob/main/model_inference/clinical_sql_benchmark_evaluator_CoT.py)

### Inferences
- For a fair reproduction, fix the API-transport bugs (add retries, handle n=9 failures, bound the JSON retry loop) and document them as infrastructure fixes, not method changes. Do not copy the original's habit of silently turning API errors into SQL text.
- If the local scorer is a reimplementation of the CLINSQL rubric scorer, it should avoid the `"1" in response` fallback, or log every judge failure, and say that this differs from the official scorer.
